# Интеграция с Jira

Задачи в Jira заводит **плагин** `jira-ticketing`. Встроенной интеграции
больше нет: Hub не хранит адрес Jira, не ходит в неё сам и не знает про её
поля — всё это знание живёт в плагине.

Как подключить каталог плагинов и установить сам плагин — на странице
[Официальные плагины](plugins-official.md). Здесь — то, что относится
именно к Jira: где что настраивается, словарь шаблонов и особенности самой
Jira, проверенные на живых площадках.

!!! warning "Обновление с версий до 0.33"

    Прежние переменные окружения `FALLBACK_JIRA_URL`,
    `FEATURE_JIRA_REVERSE_SYNC`, `JIRA_REVERSE_SYNC_INTERVAL_MINUTES`,
    `JIRA_REVERSE_SYNC_BATCH_SIZE`, `JIRA_SYNC_WORKERS` и
    `FEATURE_JIRA_ENGINE_ROUTING` **удалены**. Оставленные в конфигурации,
    они просто не читаются. Настройки проектов переносятся в конфигурацию
    плагина — порядок перехода согласуйте с поставщиком: возврата к
    встроенной дороге не предусмотрено.

## Где что настраивается

Настройки лежат на трёх уровнях, и это разделение не формальное — у каждого
уровня свой владелец.

| Уровень | Где | Что там |
| --- | --- | --- |
| Конфигурация установки плагина | Администрирование → Плагины → Настроить | Адрес Jira, способ входа, значения по умолчанию для всех проектов |
| Конфигурация плагина для проекта | Правка проекта → учёт задач | То же, но для одного проекта: своя доска, свой ключ, свои шаблоны и свой секрет |
| Настройки проекта в Hub | Правка проекта → учёт задач | Что делает **ядро**: какой провайдер привязан, заводить ли задачу автоматически, группировать ли похожие находки, цепочка переходов после создания |

Правило простое: адрес системы, ключи проектов, шаблоны и токены — знание
плагина; «когда заводить задачу» — знание Hub.

## Основные настройки плагина

| Настройка | Обяз. | Назначение |
| --- | --- | --- |
| `base_url` | да | Адрес Jira |
| `project_key` | да | Ключ проекта по умолчанию |
| `auth_method` | | Способ входа: по паре «почта + токен» либо OAuth |
| `email`, `api_token` | | Пара для первого способа; токен — секрет |
| `client_id`, `client_secret` | | Пара для OAuth; второе — секрет |
| `issue_type`, `issuetype_id` | | Тип создаваемой задачи |
| `issuetype_by_engine` | | Тип задачи в зависимости от сканера |
| `projects` | | Курируемый список целей, из которого выбирает оператор |
| `labels`, `priority_id` | | Метки и приоритет |
| `payload_template` | | Шаблон **всего тела запроса** к Jira |
| `summary_template`, `description_template` | | Шаблоны заголовка и описания |
| `partial_summary_template`, `partial_description_template`, `partial_row_template` | | Те же шаблоны для полуручного режима |
| `extra_fields`, `extra_params` | | Дополнительные поля Jira |
| `value_maps` | | Соответствия «значение Hub → значение Jira» |
| `transition_fields` | | Поля, требуемые при переводе по статусу |

## Два режима

**Полная автоматизация.** Hub сам обращается к Jira и заводит задачу.
Применяется `payload_template` — шаблон всего тела запроса.

**Полуручной режим.** Hub не создаёт задачу, а отдаёт человеку ссылку на
предзаполненную форму Jira. Применяются шаблоны `partial_*`.

!!! note "В полуручном режиме цель выбирает набор полей формы"

    У каждой записи курируемого списка `projects` свои `extra_params`,
    поэтому выбранная цель определяет не только проект Jira, но и состав
    полей формы. Несовпадение цели — отказ, а не молчаливый откат к первой:
    иначе форма открывается для чужого проекта, и выглядит это как успех.

    Ссылка ужимается до 3800 символов. Предел не круглый намеренно: браузер
    отбрасывает адрес длиннее 4096, и ссылка между этими числами молча не
    открывается.

## Шаблоны

### Плейсхолдеры

**Сама находка**

| Плейсхолдер | Что подставляется |
| --- | --- |
| `{id}`, `{title}`, `{description}` | Идентификатор, заголовок, описание |
| `{severity}` | `CRITICAL`, `HIGH`, `MEDIUM`, `LOW`, `INFO` |
| `{status}` | Текущее состояние |
| `{engine}` | Сканер, нашедший проблему |
| `{cve}`, `{cwe}` | Идентификаторы уязвимости и класса слабости |
| `{fingerprint}` | Отпечаток из отчёта |
| `{secret_type}` | Тип найденного секрета |
| `{sla_expires_at}` | Срок устранения |
| `{first_seen_at}`, `{last_seen_at}` | Когда обнаружена впервые и в последний раз |
| `{first_seen_at_date:ФОРМАТ}`, `{last_seen_at_date:ФОРМАТ}` | То же с заданным форматом даты, например `{first_seen_at_date:d/MMM/yy}` |

**Где находится**

| Плейсхолдер | Что подставляется |
| --- | --- |
| `{resource}` | Обобщённое местоположение |
| `{ip}`, `{host}`, `{domain}` | Адрес, узел, домен |
| `{port}`, `{port_range}`, `{protocol}` | Порт, диапазон портов, протокол |
| `{service}` | Определённый сервис |
| `{file_path}`, `{line_start}`, `{line_end}` | Файл и строки для находок в коде |
| `{code}`, `{code_link}` | Фрагмент кода и ссылка на него |
| `{open_ports_list}` | Перечень открытых портов узла |

**Контекст Hub**

| Плейсхолдер | Что подставляется |
| --- | --- |
| `{product}`, `{product_name}` | Продукт |
| `{project}`, `{project_name}` | Проект |
| `{hub_url}` | Ссылка на находку в Hub |
| `{finding}` | Сводное представление находки |
| `{members_list}` | Участники |

**Группы находок**

| Плейсхолдер | Что подставляется |
| --- | --- |
| `{count}` | Количество однотипных находок |
| `{findings_list}` | Их перечень |
| `{tags:РАЗДЕЛИТЕЛЬ}` | Метки через разделитель: `{tags:, }`, `{tags:\n}`, `{tags: ~ }` |
| `{all_tags:РАЗДЕЛИТЕЛЬ}` | Все метки группы без повторов, по алфавиту |
| `{agg:ПОЛЕ}` | Собрать значения поля по всем находкам группы |
| `{agg_or:ГРУППА:ПОЛЕ:ИНАЧЕ}` | То же с запасным значением |
| `{agg_or_map:ГРУППА:ПОЛЕ:КАРТА:ИНАЧЕ}` | То же с подстановкой по карте `value_maps` |
| `{map:...}`, `{prop:...}` | Подстановка по карте значений и по произвольному свойству |

**Разметка Jira**

`{code}`, `{noformat}`, `{panel}` — вставляются как есть, чтобы задать
форматирование в разметке Jira.

!!! note "Подстановка идёт ровно одним проходом"

    Значение, подставленное на первом шаге, дальше как шаблон не
    разбирается: находка с текстом `{cve}` в заголовке не вытянет в задачу
    ещё одно поле. Неизвестный плейсхолдер остаётся текстом — так опечатка
    в шаблоне видна, а не спрятана.

    Экранирование выбирается по полю-получателю: заголовок задачи —
    обычный текст, описание — разметка Jira. Значения приходят из отчётов
    сторонних сканеров, поэтому это не косметика: без экранирования
    подставленная строка может стать в задаче живой ссылкой или картинкой,
    подгружаемой при каждом открытии.

### Пример

```
partial_summary_template: "[{severity}] {title} на {resource}"
partial_description_template: |
  *Критичность:* {severity}
  *Ресурс:* {resource}
  *Сервис:* {service}

  *Описание:*
  {description}

  *Метки:* {tags:, }

  *Источник:* Security Hub, продукт {product} — {hub_url}
```

## Возврат статуса из Jira

Закрытие задачи в Jira закрывает находку в Hub. Работают два пути, и оба
ведут в одну и ту же обработку — со снятием нарушения срока устранения,
уведомлением и записью в журнал:

- **вебхук** — Jira сообщает Hub об изменении сразу;
  адрес вида `POST /api/v1/webhooks/ticketing/<id проекта>/<секрет>`,
  секрет выдаётся при настройке проекта;
- **опрос** — Hub периодически спрашивает статус задач сам. Нужен там, где
  Jira не может достучаться до Hub.

## Автоматическое закрытие исправленных находок

Замыкает цикл: после устранения свежий отчёт сканера не содержит находку —
Hub помечает её исправленной. К Jira это отношения не имеет, но именно
здесь задача получает комментарий и перевод по статусу.

Все три условия должны выполняться одновременно:

1. глобально — `FEATURE_AUTO_VERIFY_FIXES=true`;
2. на проекте — включено «автоподтверждение исправлений»;
3. при загрузке отчёта — параметр `verify_fixes=true`.

Без всех трёх частичный скан (например, одного контейнера) закрыл бы
находки, которые он и не проверял.

Что происходит с отчётом, помеченным `verify_fixes=true`:

1. отбираются открытые находки того же сканера в том же продукте;
2. они сравниваются с находками нового отчёта по хешу дедупликации;
3. отсутствующие **не закрываются сразу** — им наращивается счётчик
   последовательных отсутствий;
4. находка закрывается только после `AUTO_VERIFY_ABSENT_THRESHOLD`
   подряд идущих проверок, давших «отсутствует» (по умолчанию три). Любое
   обнаружение сбрасывает счётчик;
5. если у закрытой находки есть задача — в неё добавляется комментарий, а
   при заданном переходе задача ещё и переводится по статусу.

!!! warning "Кворум обязателен"

    Ранняя версия закрывала находку по одному наблюдению. На работающей
    установке это дало массовое ложное закрытие: значительная часть находок
    вернулась при следующем сканировании. Значение `1` возвращает ровно то
    поведение — не ставьте его.

Пример загрузки отчёта с проверкой исправлений:

```bash
curl -X POST https://hub.example.com/api/v1/products/<id>/reports \
  -H "X-API-Key: $HUB_API_KEY" \
  -F "file=@scan.sarif" \
  -F "verify_fixes=true"
```

## Защита от обращений во внутреннюю сеть

Адрес Jira проверяется перед обращением: по умолчанию Hub не ходит на
приватные адреса, чтобы подменённый адрес не превратился в способ читать
внутренние сервисы.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `JIRA_ALLOW_HTTP` | `false` | Разрешить адрес без TLS. Только для разработки |
| `JIRA_ALLOW_LOCAL_DIAL` | `false` | Разрешить приватные адреса. Нужно для Jira во внутренней сети |
| `JIRA_BASE_URL_ALLOWLIST` | — | Список разрешённых узлов через запятую |

!!! danger "`JIRA_ALLOW_LOCAL_DIAL` в облаке"

    В публичном облаке этот флаг открывает доступ к сервисам метаданных
    (AWS IMDS, метаданные GCP). Включайте его только во внутренней сети и
    вместе с `JIRA_BASE_URL_ALLOWLIST`.

## Учётная запись в Jira

### Jira Cloud

1. Завести служебную учётную запись, например `hub-bot@example.com`.
2. Профиль → Security → Create API token.
3. В проекте Jira выдать ей роль с правом создавать задачи.
4. В настройках плагина: способ входа «почта и токен», `email` — адрес
   учётной записи, `api_token` — созданный токен (не пароль).

### Jira Data Center

1. Завести пользователя `hub-bot`.
2. Профиль → Personal Access Tokens → создать токен.
3. В настройках плагина: способ входа «почта и токен», `email` — имя
   пользователя, `api_token` — созданный токен.

## Проверка

1. Убедитесь, что плагин **включён** и привязан к проекту: установка сама по
   себе задачи не заводит.
2. Переведите любую находку в состояние «подтверждена» — при включённом
   автосоздании появится задача. В полуручном режиме в карточке находки
   появится ссылка на предзаполненную форму.
3. Закройте задачу в Jira и проверьте, что находка в Hub перешла в
   «исправлена».

## Типовые проблемы

| Признак | Что проверить |
| --- | --- |
| Кнопки заведения задачи нет | Привязан ли провайдер к проекту; включён ли плагин |
| Отказ «нужно выбрать провайдера» | Провайдеры установлены, но к проекту ни один не привязан |
| `401` при создании | Способ входа и учётные данные. Для Jira Cloud нужен API-токен, а не пароль |
| `403` при создании | У учётной записи нет права создавать задачи в этом проекте |
| Переход по статусу отклонён | Цепочка переходов ведёт по статусу, недоступному в схеме работ Jira |
| Обращение блокируется | Jira во внутренней сети — нужен `JIRA_ALLOW_LOCAL_DIAL` вместе с `JIRA_BASE_URL_ALLOWLIST` |
| Находки закрываются массово | Передаётся ли `verify_fixes` при частичных сканах; каков `AUTO_VERIFY_ABSENT_THRESHOLD` |
